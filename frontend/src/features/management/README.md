# Management feature (unified RM / CA portal)

**Purpose and scope:** the Management portal screens for Task 10B (#10; MG-01, MG-03, MG-08, MG-10; DDR-114). Backend: the `management` module (scoped read views, staff access, exports) plus the owning modules' existing routes for actions (kitchen settings and reject, delivery manage). Every view is scoped by the backend; the UI only hides controls. Reports are Task 13, realtime Task 11A (`shared/realtime`), AI Task 15.

## Behaviour

- **Overview:** active orders by status, items needing attention (each links to its screen) and kitchen intake, from persisted data only. Revenue and KPIs are not shown and say why (DDR-44, Task 13).
- **Orders & Exceptions:** filters status, kitchen, agent, exception flag and dates (last 7 days by default, at most 31); 50 per page; "Export CSV" downloads the current filtered view (≤ 5,000 rows, audited). The detail shows items and the fulfilment, payment and assignment timeline with actor and reason. Actions appear only where the rules allow them: assign or reassign to a free online agent, approve or return a failure request, issue a new delivery code after an exception, "Cannot fulfil". A failed delivery reads "Refund decision pending: exceptional refunds disabled".
- **Delivery Operations:** agents with availability and live work, force offline with a reason; live offers and deliveries with the latest position (Simulated GPS badged) in a table and a lazily loaded map; advisory assignment suggestions for unassigned accepted, preparing and ready orders follow least-recently-offered ordering and never offer or assign an agent. Manual assignment and manager override remain unchanged. The tile server is configurable and a tile failure falls back to the table.
- **Menu & Inventory:** read-only stock, reserved, available, thresholds and the latest 100 ledger rows, with the Test stock label. Changes stay with the Kitchen Manager.
- **Payments:** refunds read-only; exceptional approval and CA override read "Disabled: no threshold configured (DDR-44)"; no manual refund.
- **Staff & Access:** add a role (name, mobile, role, region, kitchen for kitchen roles, reason); remove a role, deactivate or reactivate with a reason. The RM's choices are Kitchen Staff, Kitchen Manager and Delivery Agent; only a CA sees Regional Manager. Your own row has no controls. A removal or deactivation blocked by an agent's active delivery shows the backend's message.
- **Audit logs:** filters action, target type, actor role and dates (≤ 31 days); 50 per page; audited CSV export. Unscoped events (e.g. exports) appear only in Global Audit Logs.
- Screens update live from region hints (DDR-115) and say "Live"; while the socket is down they poll every 10 s and say "Live updates paused · updates every 10 s"; every action needs a reason and refreshes all management views.

## Management AI Copilot (Task 15)

- CA and RM can open the read-only Copilot; only CA can change the configured logical model.
- Provider keys and routing configuration never appear in the UI. Knowledge is labelled "pending approval" until DDR-46.
- Conversations retain six turns; users can delete their own conversations; request logs contain metadata only.

## Operational Actions (Task 15A; DDR-120)

The CA-only `/management/actions` route uses a separate simulated Actions harness. A typed request produces an exact-change dialog; confirmation sends a UUID idempotency key and the backend rejects changed state. Kitchen settings, agent assignment, dish-unavailability decisions and TEST menu publication reuse their owning services. Promotions, review moderation, regional settings and exceptional refunds state why they are unavailable. RM cannot open the page or use the endpoints.

## Builder Agent (Task 15C; DDR-68, DDR-70, DDR-71, DDR-80)

The CA-only `/management/builder-agent` page asks the `strong` model for a small change, runs unit tests in a disposable committed-HEAD workspace, and presents the exact diff before confirmation. Confirmation opens a pull request on a new `builder-agent/*` branch; the client has no main-branch update or merge operation. RM and all other roles receive 403 responses from the backend. Reviews, tickets, orders, notes and RAG documents are not loaded into model context.
