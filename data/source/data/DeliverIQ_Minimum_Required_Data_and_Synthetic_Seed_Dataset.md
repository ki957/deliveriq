# DeliverIQ — Minimum Required Application Data & Synthetic Seed Dataset

**Document:** DeliverIQ Data Requirements and Seed Data Pack  
**Version:** 1.0  
**Date:** 11 November 2026  
**Purpose:** Identify the minimum data required to operate and test the DeliverIQ POC, and provide synthetic seed records.

---

# 1. Objective

This document answers two questions:

1. What data does DeliverIQ need to run the application?
2. Which minimum records should we create now for development and testing?

The goal is to avoid unnecessary data collection and avoid duplicating information that already exists.

## 1.1 Existing data — do not regenerate

| Data | Current status | Action |
|---|---|---|
| Menu food catalogue (approximately 104 dishes) | Already provided by product owner | Import existing catalogue |
| Ingredients associated with each food | Already provided by product owner | Import existing ingredient mapping |
| Dashboard colour schemas | Already provided by product owner | Reuse existing design tokens |
| Product/portal requirements | Defined in DeliverIQ planning | Implement from approved requirements |

**Important:** The actual menu and ingredient source files must be used during repository/data import. This document does not replace them. Do not create duplicate dishes or ingredients.

# 4. Minimum knowledge data for the three AI systems

These are separate knowledge sets. Do not merge their documents.

| RAG collection | Minimum content to prepare | Must not contain |
|---|---|---|
| Customer RAG | Menu descriptions, customer FAQs, ordering rules, delivery/cancellation/refund policies | Kitchen SOPs, internal recipes, stock quantities, staff data, margins |
| Kitchen RAG | Approved recipe versions, kitchen SOPs, approved food-handling guidance, equipment troubleshooting | Customer contact details/history, management-only policies |
| Management RAG | Operational SOPs, refund/promotion policies, escalation procedures, KPI definitions | Unrestricted customer records, kitchen-private recipe details |

For each knowledge document, minimum metadata:
- Document ID.
- Title.
- Portal/collection.
- Category.
- Version.
- Approval status.
- Owner/approver.
- Effective date.
- Region/kitchen scope if applicable.
- Source reference.
- Content hash.
- Active/withdrawn status.

Start with a small approved set:
- Customer: 5–10 FAQs/policy documents.
- Kitchen: 3–5 SOP/food-handling documents plus approved recipe source.
- Management: 3–5 operational/policy documents plus KPI definitions.

These are suggested initial test quantities, not mandatory production document counts.

# 7. Data that should NOT be collected for the POC

Avoid unnecessary personal or operational data:

- Real customer phone numbers.
- Real customer addresses.
- Real payment credentials or bank details.
- Aadhaar, PAN or other government identifiers.
- Customer date of birth unless a specific approved requirement exists.
- Real delivery-agent personal documents.
- Unnecessary customer location history.
- Real supplier bank details.
- Production secrets or API keys in seed files.
- Real customer support conversations.
- Unapproved health/allergen claims.

Use synthetic identities and test-only location data.

# 11. Final recommendation

For the first working DeliverIQ dataset, prepare only:

1. One region and one kitchen.
2. Six test identities—one for each role.
3. One synthetic customer address.
4. Delivery/serviceability configuration.
5. Existing menu and ingredient data imported as-is.
6. Approved dish prices and recipe quantities.
7. Opening stock for the ingredients used in test orders.
8. Three simulated payment methods.
9. Four controlled order scenarios.
10. A small approved knowledge set for each RAG portal.

Do not generate fake production-scale customer data, hundreds of orders or supplier records yet. Build the smallest dataset that proves the full workflow, role boundaries and AI knowledge isolation.
